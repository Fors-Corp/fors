# Fors design: roadmap-execution

> **Status: design-panel draft, 2026-09-19.** Produced by one subsystem architect working alone. Where this conflicts with `docs/PLAN.md` (section 4, Resolutions), PLAN.md wins. Cross-design conflicts are catalogued in `reviews.md`.

## Summary

Fors is executable solo-with-agents if and only if every goal claim is bound to a measurement that exists before the claim does, so M0 (the benchmark harness the owner asked for) is not a warm-up but the permanent contract layer for G1/G3/G4 and part of G2. The program runs M0..M12 over roughly six and a half years: harness (3 weeks), frontend + reference interpreter (Y1), aarch64/Mach-O dev backend with its own ad-hoc code signer (Y1-2), memory/error/trap semantics and contracts syntax (Y2), capabilities plus declarative capability-confined build and signed packages (Y2, and that is the v0.1 public release), own optimizing backend (Y3, the single longest and riskiest item), SIMD/SPMD plus structured fork/join parallelism (Y3-4), optimizing backend v2 with PGO (Y4), x86_64/ELF plus DWARF/debugger/sanitizers (Y4-5), GPU single-source on Metal then SPIR-V then PTX (Y5), distributed (Y5-6), NPU (Y6), then the SMT prover tier, secret types hardening, public registry and self-hosting into 1.0 (Y6-7). Nothing owner-mandated is dropped; gates only re-sequence. The critical path is frontend -> dev backend + Mach-O incremental/signing -> semantics freeze -> optimizing backend, and everything accelerator-shaped hangs off the semantics freeze, which is why the freeze is treated as the project's most important calendar event. Banning LLVM costs roughly 18-24 months of extra backend work and pushes G1 from "parity in 3-5 years" to "parity in 5-7 years", with the honest interim claim being "fastest builds, no-UB safe subset, confined dependencies, best-in-class parallel efficiency, competitive-but-not-leading scalar codegen". AI agents are used in three sized lanes (haiku for mechanical high-volume ISA tables and kernel ports, sonnet for one-pass-per-task bounded implementation against pre-written acceptance tests, opus only for IR/semantics architecture, miscompile root-cause, and adversarial security review), with a two-session rule that the agent writing the acceptance tests is never the agent implementing the feature. The repo is one Cargo workspace plus bench/, spec/, tests/, std/, with pre-merge CI under five minutes on macOS arm64 and a nightly heavy tier, and benchmarks never run in cloud CI but only on one pinned box with a published noise floor. Marc's personal 5-10 line contributions are placed at the points where a single constant or predicate encodes a value judgement: the harness aggregator, the declaration fingerprint, the dirty-page rehash set, the parameter-convention default, the capability implication lattice, the semver capability-break predicate, the spill priority, the steal victim, and the deterministic reduction order.

## Design

## 1. M0: the benchmark harness (the thing that must exist first)

`bench/` is stdlib-only Python 3 and outlives every compiler decision.

```
bench/runner/{cli,spawn,metrics,pin,aggregate,schema,report,compare}.py
bench/adapters/{c,rust,zig,go,swift,java,js,python,fors}.json   # build+run+version probe
bench/kernels/<kernel>/{spec.md,<lang>/...}
bench/corpus/gen.py            # synthetic 1k/10k/100k-line sources per language
bench/results/*.jsonl          # append-only, provenance-stamped
bench/METHODOLOGY.md, bench/NOISE_FLOOR.md, bench/CLAIMS.md
```

**Metrics** per (kernel, language, config): compile wall time (link included), run wall time, user+sys CPU, peak RSS (`rusage` via `wait4`), binary size stripped/unstripped, startup time (empty-main per language), parallel scaling 1..6 P-cores and 1..8 all-cores. **Correctness gate:** every kernel prints one canonical `CHK <hex>` line; integer kernels hash exact bytes, FP kernels hash a quantized reduction (relative 1e-9) so a legitimately different summation order still passes. **Fairness rules, written down before Fors exists:** expert-reviewed C and Rust baselines (the exact confound that discredited prior energy rankings), `-march=native` and a portable-baseline column, JVM/JS warmup declared per kernel, Python stdlib-only with a separate annotated "with NumPy" column, GC tuning disclosed. **Noise discipline:** ABAB interleaving, >=10 runs, trimmed mean + p95, a pre-run gate that aborts on AC/thermal/load violation, and a measured noise floor below which deltas are reported as "no change". `bench/CLAIMS.md` maps each goal to the metric that falsifies it.

**Fors joins via `adapters/fors.json` only** - one kernel at a time, harness unchanged - and joins the compile-speed axis at M1, before it can run anything.

## 2. Critical path and ordering of "everything in v1"

frontend/query DAG -> dev backend + Mach-O patch/sign -> **semantics freeze** -> optimizing backend -> SIMD/parallel -> GPU -> distributed -> NPU. Everything accelerator-shaped is downstream of the freeze, so the freeze (end of M7) is the program's most important date. Security enters early and cheaply (M3 semantics, M4 capabilities + build + packages, secret types hardened in M12); the SMT prover tier and the public registry enter last because neither is on any other milestone's critical path. Nothing is dropped; gates re-sequence only.

**Honest cost of no LLVM:** ~18-24 extra months of backend work, G1 parity slips from Y3-5 to Y5-7, and the interim public claim must be "fastest builds, no-UB, confined dependencies, best-in-class parallel efficiency, competitive scalar codegen". The gap closes through structural aliasing from parameter conventions (no metadata to drop), full layout control incl. SoA types, explicit SPMD vectorization instead of auto-vectorization heroics, a sea-of-nodes mid-IR with e-graph peepholes, and PGO as a first-class content-addressed build input.

## 3. Repo layout

Single Cargo workspace at the root: `crates/fors-{cli,lex,parse,ir,sema,query,comptime,interp,target,backend-dev,backend-opt,obj,link,dwarf,caps,build,pkg,lsp,fuzz,diff,runtime,gpu}` plus `bench/`, `spec/` (numbered chapters + `rfcs/NNNN-*.md` + ADRs), `tests/{conformance,snapshot,security,differential}`, `std/`, `tools/`, `ci/`. Hard rule: no crate over ~15k lines (keeps Rust incremental builds tolerable for four years).

## 4. CI and the testing pyramid

**Pre-merge (macOS arm64, <5 min):** build, clippy, unit tests, snapshot tests (IR dumps, diagnostics, asm), conformance suite under all available execution configs, 60-second fuzz smoke. **Nightly (self-hosted):** 8h structure-aware fuzz + IR-level random program generation, full 3-way differential (interpreter vs dev vs opt - a Rustlantis-class generator is the only thing that makes a two-tier backend honest), security conformance (adversarial dependency suite, Juliet CWE subsets, capability-escape attempts), bit-for-bit reproducibility (build twice, compare hashes), unsafe-inventory count, and the benchmark run on the pinned box with regression gating at noise-floor + 3%.

Pyramid, bottom to top: unit -> snapshot -> conformance (every test cites a spec clause; a feature without a clause-citing test does not exist) -> fuzz -> differential -> security conformance. Coverage target is clause coverage of the spec, not line coverage.

## 5. Spec and docs cadence

Spec-first: every semantic decision is an RFC in `spec/rfcs/` before code, and the spec is the merge blocker, not the documentation afterthought. One "spec day" per month reconciles spec to implementation; `fors spec --clause 7.3` prints the clause from the shipped binary. Austral's bound is the target: a spec that fits in one head. Gates: spec v0.1 at M1 (structure + TBDs), v0.5 at M4 (v0.1 release), **v1.0-beta = semantics freeze at M7**, v1.0 at M12.

## 6. Risk gates (pivot, never drop scope)

- **M2:** stencils not passing 10k differential programs by week 10 -> switch the dev tier to direct emission.
- **M2:** ad-hoc signing blocks in-place patching -> patch-to-temp + rename (still no full relink); if that fails, incremental link at object granularity and the sub-50ms target moves to M8.
- **M5 (the big one):** >1.6x off clang geomean after 12 months -> re-sequence: pull PGO and the vector/loop work ahead of scalar parity (more quality per engineering hour), narrow the first quality claim to the named kernel class, open the backend crate publicly to recruit contributors, and push GPU out one milestone. No LLVM.
- **M6:** parallel efficiency <80% on regular kernels -> reduce to a smaller structured-parallel surface and fix determinism policy first.
- **M9:** multi-vendor GPU cost exceeds budget -> Metal + SPIR-V ship, PTX becomes a post-1.0 backend.
- **M7:** freeze slips 2 quarters -> self-hosting slips with it; never self-host on unfrozen semantics.

## Interfaces other subsystems must honor

- Every subsystem must emit machine-readable timings: `fors build --timings=json` and `fors run --metrics=json` with a schema the M0 harness already consumes. A subsystem that cannot be measured by the harness cannot make a claim in the README.
- Frontend owner: the SoA semantic IR must be versioned and serializable to a stable binary form, because the reference interpreter, the dev backend, the optimizing backend, and the differential fuzzer are four independent consumers of it. IR version bumps require a migration note in spec/rfcs.
- Frontend owner: aliasing, ownership and isolation-domain facts must be structural in the IR (instruction/operand shape), never droppable metadata - the optimizing backend's only route to closing the LLVM gap depends on this.
- Semantics owner: trap set, integer/FP semantics, pointer provenance, and the failure/error ABI must be frozen by end of M3 and unchanged after the M7 freeze. Two backends can only be held to bit-for-bit agreement on fully defined behaviour.
- Semantics owner: contract syntax (pre/post/invariant) and the `Secret<T>`/constant-time type qualifiers must exist in the grammar from M3 even while runtime-checked-only and unenforced respectively, because adding them later is a breaking change to every signature.
- Parallelism owner: spawn/sync must be real IR instructions (Tapir-style) landing in M6, and the deterministic-vs-fastest reduction-order policy must be a declared language decision with a spec clause, not a backend detail.
- Parallelism owner: the SIMD/portable-vector type design, including whether scalable vectors (SVE/RVV) are in the type system, must be an accepted RFC before M6 code starts, since GPU (M9) and NPU (M11) codegen both reuse it.
- Security owner: the capability lattice, the manifest file format, and the semver rule for capability changes must be stable by end of M4 and must also answer the dynamic-linking/dlopen case before any plugin API ships.
- Backend owners: output must be bit-for-bit reproducible for identical inputs, since the reproducible-build claim and the nightly double-build CI gate depend on it; PGO profiles and autotuned schedules are content-addressed build inputs, not compiler modes.
- Backend owners: no external tool may enter the default build path. The system linker, vendor GPU drivers/runtime compilers, and an optional SMT solver are the only permitted externals, each behind a flag or a non-default tier.
- All owners: every user-visible feature ships with conformance tests citing a spec clause number in the same PR; acceptance tests are authored in a different agent session than the implementation.
- GPU/distributed/NPU owners: reuse the same source language, same IR, and same capability model - single-source only. A separate kernel dialect is out of scope for v1.

## Top risks

- The own optimizing backend (M5-M7) is the schedule and credibility risk of the whole program: no LLVM means ~18-24 extra months, the research has no cost model for what codegen quality a solo-built backend reaches, and G1 parity is not provable until Y5-7. Gate: >1.6x off clang geomean after 12 months of M5 forces re-sequencing (PGO and vector work first, narrower claim, open the crate for contributors, GPU pushed out).
- macOS is the only dev machine and Mach-O in-place patching requires owning the ad-hoc code signature; if AMFI or page-cache behaviour defeats dirty-page rehashing, the sub-50ms p95 claim - the project's most winnable headline - slips to M8 and has to be re-earned via object-granularity incremental linking.
- Scope: 'everything in v1' plus solo execution means ~6.5 years to 1.0 with a 12-month error bar. The named historical failure mode is exactly this (Vale stalled mid-roadmap chasing novel mechanisms). The only defence is that gates re-sequence rather than drop, plus a real public v0.1 at M4 so value lands 5 years before 1.0.
- Semantics freeze slippage cascades: self-hosting, the prover tier, and every accelerator backend hang off it. Each quarter of frontend/semantics churn past M7 costs roughly a quarter on three downstream milestones simultaneously.
- AI-agent-generated code in a project whose headline claim is security creates provenance and subtle-bug exposure. Defences (opus review gate on unsafe/spec diffs, two-session test authorship, published shrinking unsafe inventory, 3-way differential fuzzing) reduce but do not eliminate it; a single agent-introduced miscompile discovered by a third party after a security claim is published would be disproportionately damaging.
- No local CUDA or NPU hardware and a single bench machine: M9-M11 depend on rented accelerators and vendor toolchains that churn faster than the plan, and one throttled or busy laptop can silently poison the entire performance record that all public claims rest on.
- Benchmark credibility attack: publishing performance numbers for a new language invites the V-language outcome. Mitigations are the pre-published methodology, expert-reviewed C/Rust baselines, the noise floor rule, and never claiming a delta the harness cannot reproduce - but one sloppy graph early undoes years of it.
- Parallel determinism is an unmade decision that blocks M6: race-freedom does not give reproducible FP reductions or reproducible work-stealing schedules, and choosing 'deterministic by default' costs measurable performance while choosing 'fastest by default' costs the verification and reproducibility story.
- Unglamorous unavoidable costs that historically stall hobby languages and are absent from all five surveys: per-triple ABI edge cases, DWARF at -O, sanitizers, allocator quality (which often dominates real-application performance more than codegen), and stdlib breadth (comparable in effort to the compiler itself). M8 and M12 carry these; if they are underestimated the language 'works on the author's laptop' and nowhere else.
- Solo continuity and funding: no funding plan over a 6.5-year horizon, permissive licensing plus a single BDFL invites a resourced fork exactly when the backend becomes good, and one person's illness or burnout is an unmitigated single point of failure.

## Decision points for Marc to code personally

- M0, bench/runner/aggregate.py, `summarize(samples)` (~8 lines): min vs median vs 10% trimmed mean vs p95 for wall time. Trade-off: min is the cleanest signal of the machine's capability and the most flattering; trimmed mean is what a user experiences. This choice silently shapes every performance claim the project will ever make - pick it consciously, and record the reason in the docstring.
- M0, bench/runner/pin.py, `preflight_gate()` (~10 lines): the abort predicate (AC power, thermal pressure, 1-minute load average, Spotlight state). Trade-off: strict gating means runs abort often on a laptop; loose gating means quietly corrupt data. Decide which failure you prefer.
- M0, bench/kernels/checksum.py, `fp_checksum(values)` (~6 lines): quantization scale for floating-point kernel checksums. Trade-off: too tight rejects a legitimate different-but-correct summation order (and thus rejects vectorization); too loose lets a real numerical bug pass the correctness gate.
- M1, crates/fors-ir/src/inst.rs, index width choice for `Ref(u32)` vs `Ref(u64)` (~5 lines of type + const): caps program size at ~4B IR nodes but halves IR memory traffic. The whole compile-speed thesis is a cache-locality thesis, so this is the cheapest large lever in the compiler.
- M1, crates/fors-query/src/hash.rs, `decl_fingerprint()` (~10 lines): exactly which bytes enter a declaration's content hash - do doc comments, spans, or attribute order count? Trade-off: including too much causes spurious invalidation cascades (kills the p95 incremental target); including too little is a correctness bug that produces stale code.
- M2, crates/fors-obj/src/macho/codesign.rs, `dirty_pages()` (~8 lines): the set of 4K pages whose CodeDirectory hashes must be recomputed after a patch. Trade-off: over-approximate and re-signing dominates the rebuild; under-approximate and the kernel refuses to load the binary. This is the single predicate on which the sub-50ms macOS claim rests.
- M3, crates/fors-sema/src/convention.rs, the `ParamConvention::default_for()` rule (~6 lines): is `let` the default for all types, or size-dependent? Trade-off: one uniform rule is teachable and predictable; a size threshold is faster but makes ABI and performance depend on a type's byte count, which users will discover the hard way.
- M3, crates/fors-sema/src/failure.rs, `FailureAbi` selection (~8 lines): returned flag vs second return register vs unwinding. Trade-off: register-pair is fastest and hurts binary size on cold paths; unwinding is zero-cost on the happy path but complicates FFI, the no-UB guarantee, and the dev backend. Pick one and write the sentence explaining why.
- M4, crates/fors-caps/src/lattice.rs, `Capability::implies()` (~10 lines): the partial order - does `fs(dir=/x)` imply `fs(read)`? does `exec` imply `fs`? Trade-off: a coarse lattice is auditable but forces over-declaration; a fine one is precise and becomes a soundness surface. This predicate IS the security claim.
- M4, crates/fors-pkg/src/semver.rs, `capability_change_is_breaking()` (~6 lines): does a dependency gaining `net` in a patch release require a major bump and an explicit user re-approval? Trade-off: strict means constant friction and ecosystem churn; lax reintroduces exactly the xz failure mode the project exists to prevent. Probably the most consequential six lines in the package manager.
- M5, crates/fors-backend-opt/src/regalloc/spill.rs, `spill_priority()` (~10 lines): loop-depth weight vs use-count vs live-range length. Trade-off: this one heuristic moves inner-loop performance by double-digit percentages and is the most direct place to feel what an optimizing backend actually is.
- M5, crates/fors-backend-opt/src/cost.rs, `inline_benefit()` (~8 lines): the call-site threshold. Trade-off: aggressive inlining buys scalar performance and costs i-cache, binary size, and compile time - i.e. it trades G1 directly against G3, which is the central tension of the whole project in one constant.
- M6, crates/fors-runtime/src/sched.rs, `steal_victim()` (~6 lines): random vs nearest-neighbour victim selection on a 6P+2E asymmetric core layout. Trade-off: random is provably good asymptotically; locality-aware wins on this specific machine. Also the place to decide whether E-cores participate at all.
- M6, crates/fors-ir/src/parallel.rs, `reduction_order()` (~8 lines): fixed binary-tree reduction (bit-reproducible across thread counts) vs schedule-order reduction (faster). Trade-off: this is the parallel-determinism decision, made concrete - write it here and the spec clause follows.
- M7, crates/fors-backend-opt/src/pgo/profile.rs, `edge_weight_decay()` (~6 lines): how a stale checked-in profile ages out as source drifts. Trade-off: trusting old profiles is fast and can be badly wrong; discarding them makes PGO useless in practice.
- M8, crates/fors-dwarf/src/lines.rs, the `is_stmt` policy for optimized code (~8 lines): which of several merged source positions gets the breakpoint. Trade-off: honest (many is_stmt=false rows, debugger jumps around) vs friendly (lies slightly about where you are).
- M9, crates/fors-gpu/src/metal/launch.rs, `grid_shape()` (~8 lines): threadgroup sizing heuristic from the kernel's declared vector width and register pressure. Trade-off: portable-and-mediocre default vs per-device autotuned data artifact.
- M12, crates/fors-sema/src/secret.rs, the `declassify` rule (~6 lines): what syntactic act is required to turn a `Secret<T>` into a public value, and whether it is auditable per-module. Trade-off: too easy and the type is decoration; too hard and nobody writes crypto in Fors.
